# 使用说明（给你自己看，不用发给译员）

## 包里有什么

| 文件 | 用途 |
|---|---|
| `00-翻译规则.md` | **发给译员的唯一规则**。连同批次文件一起丢给大模型即可 |
| `01-总表.jsonl` | 全部待译条目，一行一条。用于备查、筛选、自己派活 |
| `02-示例-已完成.jsonl` | 13 条库内定稿条目，六语齐全。可当 few-shot 示例贴给模型 |
| `03-待补原文-不译.txt` | 59 条**不是翻译问题**的条目（原文是文件名/抬头/空白），须回原页补题 |
| `04-批次索引.csv` | 批次清单，含条数与语种需求，最后一列可自己登记进度 |
| `批次/<国别>/<国别>-NN.jsonl` | 实际派活的文件，每批 100 条 |

合计待译 **15,573 条**：PH 14,646、ID 720、MY 140、TH 51、LA 8、VN 8。

## 怎么派

1. 打开一个批次文件（如 `批次/PH/PH-01.jsonl`），把 `00-翻译规则.md` 一起给模型。
2. 一句话交代："按规则翻译这个文件，输出 JSONL。" 100 条一次吃完大概 8–15k 字输出，
   多数模型一次能吃完；吃不下就让它分两次输出，或把批次拆成两半。
3. 模型输出存成同名 `.out.jsonl`，例如 `PH-01.out.jsonl`，放回同一个 `批次/PH/` 目录。

> 中文模型在 `th`（泰文）上最容易崩，建议泰文挑一个泰语强的模型，或先跑 3 条看质量再放量。

## 怎么回收

译好的 `.out.jsonl` 攒到一个目录（比如桌面 `回填/`），告诉我路径，我跑：

```bash
node _work/title-multi/_ext_import.js <回填目录或单个文件>      # 过闸门，出台格批次
node _work/title-multi/apply-multi.js _work/title-multi/_ext_batches/<批次>.json   # 入库
node _work/title-multi/_ph_cover.js                              # 看覆盖率变化
```

校验会拦下这几类硬伤，并逐条写明原因（`_ext_bad.txt`）：

- 结构：`key` 不在清单、`need` 里的语种缺条、长度不在 2–300
- 字符集：`th` 混汉字、`zh` 混泰文、`vi/id/ms` 混汉字
- 兜底：出现 `译文 || 原文`
- 数字：文号数字全丢（直接退回）、个别语种丢（提醒）、凭空多出四位数（提醒）
- 残句：只剩英文虚词的碎片

## 分批建议

优先级按"补一条的边际价值"排：

1. **ID 720 条**（8 批）：补的是 zh+en+vi+th+ms 五语，一条顶五条，且句框固定、最好译；
   跑完 ID 就 100% 满。
2. **MY 140 / TH 51 / VN 8 / LA 8**（共 3 批）：量小，跑完这五个法域全满。
3. **PH 14,646 条**（147 批）：量最大，长题多，慢慢磨。PH 是唯一还需要大量人力的法域。

先跑 1、2（11 批），全库覆盖率能从 63.5% 抬到约 65.7%（26,761 → 27,688 / 42,121），且除 PH 外全部满格；
PH 那 147 批按周排，跑多少进多少。

## 注意

- 不要改 `01-总表.jsonl` 和批次文件里的 `src`/`have` 字段——它们是校验基准。
- 模型如果只肯输出 Markdown 表格，让它改成 JSONL 再交；表格我这边不能直接吃。
- 同一批分多次交没问题，按 `key` 合并，重复的交了也只算一次。
