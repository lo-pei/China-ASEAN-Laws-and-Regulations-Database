# 02 · 数据规范与治理

> 本文说明 CALR 的数据模型、入库流程、质量治理规则与历次批次记录。
> 与代码库同步版本：2026-10-24

---

## 一、数据分层

```
权威存储（Single Source of Truth）
  prototype/data/laws/<法规ID>.json        18,785 个文件，一法一文件
        │
        ├─ 派生 ①  条文分卷  prototype/data/{cn,intl,fulltext}/*.js
        │            按需加载，前端首屏只拉需要的
        ├─ 派生 ②  目录索引  prototype/data/{cn,intl}-catalog.js
        │            列表页与筛选用；由 fix-catalogs.js 从 laws/ 对齐生成
        ├─ 派生 ③  检索库    backend/data/calr.db（SQLite，1.6 GB）
        │            BM25 倒排 + 条文表，供后端检索
        └─ 派生 ④  向量索引  backend/data/vectors/*.npy
                     bge-m3 int8 向量，供语义召回

独立档案（不参与派生，只增不改）
  prototype/data/trans/       译文层，21 分卷，1,566 部 / 60,084 条
  prototype/data/title-zh/    中文标题档案，含来源与引擎，18,746 条
```

**红线：`data/trans/` 与 `data/title-zh/` 的内容绝不写回 `data/laws/` 的正文**。
译文只在运行时合并进内存（`CALR.fulltext.mergeTrans`），磁盘上永不混写。
例外：`title.zh` 字段作为法规元数据的一部分，允许由 `titles.zh.json` 同步（有校验器约束一致）。

## 二、法规 JSON 的数据模型

`prototype/data/laws/<id>.json`，约 30 个字段：

| 字段 | 说明 |
| :--- | :--- |
| `id` | 法规 ID（`CN-DATA-2021` / `MY-PDPA-2010` / `TH-H1139`） |
| `title` | `{zh, en, orig}` 三语标题，`orig` 为官方原文语种 |
| `country` / `countryName` | 法域代码与中文名 |
| `layer` / `pack` | 数据层（`cn` / `intl` / `fulltext`）与所属分卷 |
| `language` | 原文语种数组 |
| `level` / `category` / `status` | 法律层级 / 主题分类 / 时效性 |
| `promulgatedDate` / `effectiveDate` / `versionDate` | 公布 / 施行 / 版本日期 |
| `amendedNote` | 修正说明 |
| `issuingBody` / `docNumber` / `officialCode` | 制定机关 / 文号 / 官方编号 |
| `topics` | 主题标签数组（用于筛选与比对） |
| `coverage` | `full`（有全文）/ `catalog`（仅目录）/ `excerpt`（摘录） |
| `articleCount` / `chars` | 条文数 / 正文字符数（由实际条文统计，必须一致） |
| `source` | `{name, url}` 官方来源 |
| `articles[]` | 条文数组，见下 |
| `numberingConflict` | 译文编号无法对齐的说明（少数法规） |
| `titleFilledFrom` / `rebuiltFrom` | 数据修复留痕 |

### 条文对象

```json
{
  "id": "CN-DATA-2021-A32",
  "no": 32,
  "dupIndex": null,            // 同一部法内条号重复时用于区分（多文件合集）
  "noLabel": { "zh": "第三十二条" },
  "heading": { "zh": "数据安全保护义务" },
  "chapter": "第四章 数据安全",
  "text": { "zh": "……" }      // 原文与译文分语种存放
}
```

## 三、入库流程

### 单部法规入库

```
① 采集          官方门户 / 公报 PDF → 文本
② 结构化        识别章条编号 → articles[]；条号重复时填 dupIndex
③ 元数据        标题、机关、文号、公布/施行日期、source{name,url}
④ 落盘          prototype/data/laws/<id>.json（这是唯一的写入动作）
⑤ 派生重建      rebuild-index → build-packs → fix-catalogs → build_db → （按需）embed
⑥ 校验          node tools/verify-data.js && node tools/verify-data-home.js
```

### 派生重建命令（顺序不能乱）

```bash
node _work/merge/rebuild-index.js      # laws/index.json 统计
node _work/merge/build-packs.js        # 条文分卷 + manifest
node _work/backend/fix-catalogs.js     # catalog 与 laws/ 对齐（补缺失、删死链）
python backend/build_db.py             # SQLite（约 7 分钟）
python _work/phaseb/embed.py --level law        # 法规级向量（GPU 约 20 分钟）
python _work/phaseb/embed.py --level article    # 条文级向量（GPU 约 4 小时）
```

> **踩过的坑**：重建 DB 前必须先停后端服务，否则 `calr.db` 被占用会 `PermissionError`。

### 译文入库

```
_work/trans/returns/**/   ← 大模型返回的回执（一法一 JSON）
        │
        ├─ 校验四个维度：
        │   A) manifest 声明的分卷里确有该法规
        │   B) 分卷里每个法规 manifest 都登记了
        │   C) 译文对应法规在 laws/ 中存在
        │   D) 与回执的条文数一致
        └─ 生成 prototype/data/trans/cn-pXX.en.js + manifest.js + PROVENANCE.md
```

## 四、质量治理规则（硬约束）

| 规则 | 检查器 | 违反后果 |
| :--- | :--- | :--- |
| `articleCount` 必须等于 `articles.length` | `verify-data` A3 | 首页统计与详情页对不上 |
| `chars` 必须等于条文正文总字符数 | `verify-data` | index.json 与逐文件统计不符 |
| 同一部法内条文 `id` 唯一 | `verify-data` A3 | 索引冲突 |
| catalog 条数必须与 `laws/` 对齐 | `verify-data-home` A2 | **52% 数据在界面上不可达**（曾真实发生过） |
| 译文条号必须唯一 | `verify-data` | 违反译文层契约 |
| 译文 `lawId` 必须在 `laws/` 中存在 | `verify-data-home` A6 | 孤儿译文 |
| `titles.zh.json` 与 `laws/` 的 `title.zh` 必须一致 | `verify-data-home` A10 | 列表与详情显示不同 |
| 数据不得引用 `prototype/` 之外的路径 | `verify-data-home` A8 | 拷走 `prototype/` 就无法运行 |
| 禁用项（不得出现指定违规表述） | `scan-forbidden2` | 违反项目红线 |

> **这些不是形式检查**。catalog 与 `laws/` 脱节那次，实测导致 **9,838 部法规（52%）在界面上搜不到**，
> 首页显示 13,478 而实际 18,861。检查器就是为拦住这类问题加的。

## 五、已治理的数据缺陷（附处置方式）

### 1. 整部法被塞进 1 条（51 部，已修）

**现象**：详情页只有「第 1 条」，条文目录 1 项，条文级检索与引用全部失效。
**例**：`MY-H075`《个人数据保护法》1 条 / 33,075 字，但正文里完整保留了「第 1 条…第 146 条」标记。
**处置**（`_work/fix/split-laws.py`）：
- 识别三种条号标记：中文「第 N 条」（允许空格）、英文 `Section N`、英文 `N. `
- 只认「1,2,3… 严格递增」序列，避免把正文偶然引用的「第 X 条」当切点
- **拼接无损校验**：切分后各条 + 前言必须与原文逐字一致，否则不落盘
- 剥掉每条正文开头重复的「第 N 条」（头部已有 noLabel）
- 首条保留前言（颁布语），保证一字不丢
- 逐部备份到 `_work/fix/law-backup/`

**结果**：51 部切分成功，完整性校验 **51/51 无损**；`MY-H075` 由 1 条变 **146 条**；全库条文 **+4,293**。

### 2. 正文是「元数据侧车文件」的假法规（76 部，已删）

**现象**：点进去只有 1–2 条，内容全是「原文标题 / 官方来源 URL / SHA256 / 抓取日期 / 侧车文件」。
**两种写法**：行内字段式、Markdown 表格式（`| 原文标题 | … |`）。
**判定条件**（宁严不宽）：条文数 ≤2 且总字数 <3000 且（强信号命中 或 字段标记 ≥3）。
**处置**：**逐条人工审计**后移出到 `_work/removed-junk/`（不物理删除，附 `REPORT.json`），
再重建索引、catalog，并清理 `titles.zh.json` 中的孤儿标题。
**结果**：法规 18,861 → **18,785**，条文 334,779 → 334,703，标题清孤儿 73 条。

### 3. 完全没有标题的法规（298 部 → 已修 235 部）

**现象**：`title` 三个语种全为 `null`，界面显示空白。
**发现**：标题一直在现有字段里 —— `source.name` 形如「文莱 — Unfair Contract Terms Act」，
或正文首条含「原文标题：ARBITRATION ACT (Chapter 173)」。
**v1 失败教训**：还从 `source.url` 的文件名抽标题，一次补 286 部但质量不合格
（`Revenue-Code-Ch5-Specific-Business-Tax-S91-91-21`、`鎶曡祫淇冭繘娉昣2016`、
`UNDANG-UNDANG REPUBLIK INDONESIA NOMOR 40 TAHUN …`），**全部回退重做**。
**v2 四道过滤**：乱码检测 / URL-slug 形态检测（无空格且多连字符）/ 长度上限 90 /
文件名后缀清洗（`_2014`、`_930921`、`_EN`、`__dup2`、`_年份不详`）。
**结果**：235 部补齐，审计乱码 0、URL 断词 0、长度 2–87（中位 26）。

### 4. 泰文标题中译（571 部，已译 615 条）

**为什么不用规则词表**：571 个标题切成 971 种片段，只有 7 部能完全由高频片段组成 ——
具体法规名是唯一词，规则化只会产出中泰混杂的烂标题。

**方案**：`facebook/nllb-200-distilled-600M`（本地 CPU 推理，不依赖任何 API Key）。
**三代演进**：
| 版本 | 问题 | 修正 |
| :--- | :--- | :--- |
| v1 | 「第二千四百七十五章」（佛历年份被译成中文数字） | 先换算成公历阿拉伯数字再送模型 |
| v2 | 「บรรพ ๑」被译成「利和商业法规」 | 泰文数字 ๐-๙ → ASCII；`บรรพ N` → 第N编 |
| v3 | 部分法典名仍误译 | 已是中文的直接采用；高频法典名走术语表；552 条格式清洗 |

**环境隔离**：`transformers 4.44` 需要 `tokenizers<0.20`，而 bge-m3 嵌入要 `0.23.3`，
**硬冲突** → 变换模型装在独立目录 `_work/pylibs_ml`，两个进程各用各的，互不干扰。

**结果**：标题覆盖 18,166 → **18,746 / 18,785（99.79%）**，仍缺 39 部
（缅甸文 17 / 泰文 16 / 马来文 12 / 老挝文 11 / 柬埔寨 2 / 印尼 2，需其他语种模型）。
所有机器译文标 `engine=nllb-200-distilled-600M`、`reviewed=false`、保留 `origTitle`。

### 5. 译文编号不可对齐（5 部，列为声明例外）

**成因**：原件是多份文件的合集，各部分条号自 1 起独立编号（原文用 `dupIndex` 保留重复条号），
而译文层契约要求「条号唯一」，只能按全文顺序编 1..N，无法一一对应。
**处置**：这类译文不参与合并（`mergeTrans` 整部跳过），校验器列为「已声明的例外」而非错误；
`PROVENANCE.md` 第六节记录成因与根本解法（修正原文切分）。

## 八、数据红线（不可违反）

1. **逐字照录**：不得节选、改写、摘要原文；切分只能移动边界，不能改动文字。
2. **不编造**：不得生成原文中不存在的内容；机器翻译必须标注引擎与 `reviewed=false`。
3. **来源可追溯**：每部法规必须有 `source{name,url}`；无来源的记录视为无效。
4. **译文与原文物理分离**：`data/trans/` 绝不写回 `data/laws/` 的正文。
5. **AI 辅助生成标注**：AI 生成内容必须标「AI 辅助生成，仅供参考」，且只在对话卡片头出现一次。
6. **数据自足**：`prototype/` 单独拷走即可完整运行，不得引用外部路径。
