# 01 · 项目总览

> 中国—东盟法律法规数据库（CALR, China–ASEAN Laws and Regulations Database）
> 参赛队伍：上海对外经贸大学 一粒橡子队 · 负责人：王勃森
> 文档版本：2026-10-24（与代码库当前状态同步）

## 一、项目定位

面向涉外法律实务的**区域性官方法规数据库**：把中国与东盟十国共 **12 个法域**的官方法规文本，
做成可检索、可溯源、可对照、可引用的一站式工具。

三条主线：

| 主线 | 解决的问题 |
| :--- | :--- |
| **数据自足与可溯源** | 每部法规都能回答「从哪来、什么时候抓的、是否完整」，可点回官方页面核验 |
| **跨语言可用** | 中文用户能读到泰文、越南文、印尼文法规，反之亦然 |
| **AI 可解释检索** | 问答每条结论都附条文出处，可逐条回溯原文，不做推测性回答 |

## 四、技术栈与运行方式

### 两种运行形态（同一份代码）

```
① 纯静态（离线 / 答辩兜底）
   file:///.../prototype/index.html
   → 加载完整 data/*.js（含 intl-catalog 16.6 MB）
   → 全部检索与问答在浏览器内完成，零依赖、零网络

② 后端托管（推荐，性能与检索质量都更好）
   http://<host>:8000/
   → 后端 FastAPI 同时托管静态站与 /api/*
   → 跳过 16.6 MB catalog，改用 /api/bootstrap（2.7 KB）+ /api/laws/compact（后台补齐）
   → 检索走 BM25 + bge-m3 向量 + RRF 融合；问答走条文级向量召回
```

**同一套前端代码自动识别**：`http(s)://` 打开走 ②，`file://` 打开走 ①。

### 目录结构

```
prototype/            前端（零构建、零依赖）
  index.html          入口；按打开方式决定是否加载 intl-catalog
  assets/js/core/     store / search / qa / api / fulltext / i18n / router
  assets/js/views/    home / search / law / compare / assistant / terms / sources
  assets/css/         base / layout / components / views
  data/laws/          权威存储：18,785 个 <法规ID>.json
  data/{cn,intl,fulltext}/   条文分卷（按需加载）
  data/trans/         译文层（21 分卷，与原文物理分离）
  data/title-zh/      中文标题档案（含来源与引擎）

backend/              后端（FastAPI + SQLite + ONNX 向量）
  build_db.py         laws/*.json → calr.db
  app/main.py         API 路由
  app/db.py           只读数据库访问层
  app/search.py       法规级 BM25
  app/vectors.py      int8 向量索引 + RRF
  app/hybrid.py       BM25 + 向量融合 + 国别约束
  app/embedder.py     bge-m3 ONNX 封装（GPU 优先）
  app/security.py     CORS / 限流 / 请求体上限 / QA 鉴权
  test_api.py         13 项自测

tools/                校验工具（verify-data / verify-data-home / test-trans-layer）
rules/                项目红线与数据规范（SKILL）
docs/                 本文档集（4 份）
deliverables/         对外交付（本 4 份的 docx 版）
_work/                本地工作区（不入库）
```

### 本机运行

```bash
# 建库（首次约 7 分钟）
python backend/build_db.py

# 起服务（同时托管静态站）
pip install -r backend/requirements.txt
uvicorn backend.app.main:app --host 0.0.0.0 --port 8000
# 浏览器打开 http://127.0.0.1:8000/
```

## 五、六个关键设计取舍

| 取舍 | 理由 |
| :--- | :--- |
| **权威存储用「一法一 JSON」而非数据库** | 法规是长文本、以整部为单位使用；JSON 便于人工审查、diff、逐部替换。数据库只是派生视图，随时可重建。 |
| **译文与原文物理分离** | 红线要求「不得把译文写回原文」。译放在 `data/trans/`，运行时按需合并进内存，磁盘上永不混写。 |
| **零依赖 SPA，不做构建** | 评委只需浏览器即可运行，不依赖 Node、不依赖网络；答辩现场不会因为环境问题失败。 |
| **SQLite 而非 PostgreSQL** | 单文件、零运维、可整库备份；18,785 部 / 34 万条的规模用 SQLite 完全够，检索延迟 P50 约 0.3–0.6 秒。 |
| **ONNX 而非 PyTorch 推理** | 省掉 2.5 GB 依赖；CPU 上比 PyTorch 快 3–5 倍；配 DirectML 可直接用任意 DX12 显卡，无需装 CUDA。 |
| **RRF 融合而非加权求和** | BM25 分数量级 60–150，余弦 0–1，量纲不可比；RRF 只看排名，无需归一化也无需为每个查询调参。 |

## 六、已知不足（如实列出）

| 项 | 现状 | 影响 |
| :--- | :--- | :--- |
| 条文级向量略滞后 | 向量基于清理前的 18,861 部 / 334,779 条构建；当前库为 18,785 / 338,996 | 检索可用；被切分的 51 部法规的条文向量仍是旧的整段向量，召回精度略降 |
| 泰文标题为机器翻译 | 571 部泰文标题用 NLLB-200 译出，未人工校对 | 约六至七成可用，部分需人工复核；原文标题始终保留可查 |
| 325 部法规条号重复 | 多文件合集的各部分条号各自从 1 起编，已用 `dupIndex` 保留 | 译文层与跨层比对需特殊处理，已有 5 部列为「编号不可对齐」例外 |
| 5,321 部缺中文标题 | 多为泰文/缅文原文 | 列表显示原文标题，不空白但中文用户阅读成本高 |
| 判例数据未入库 | 已收集 1,275 页判例 PDF，其中 3 份缅甸文 OCR 不可读 | 判例检索能力缺失 |
| 缅甸文 OCR 不可用 | 本机无缅甸文识别模型 | 缅甸文法规只能保留原文，无法结构化 |

详细数据问题与处置记录见 `02-数据规范与治理.md`。
