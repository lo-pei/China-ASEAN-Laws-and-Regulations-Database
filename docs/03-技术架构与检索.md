# 03 · 技术架构与检索

> 本文说明前端架构、后端 API、检索链路、性能实测与安全设计。
> 与代码库同步版本：2026-10-24

## 一、总体架构

```
                     ┌─────────────────────────────────────┐
   浏览器 ───────────▶│  FastAPI（backend/app/main.py）      │
                     │   ├ /            静态站（prototype/）│
                     │   ├ /api/*       JSON 接口           │
                     │   └ security.py  限流/体积/CORS/鉴权 │
                     └──────────┬──────────────────────────┘
                                │
              ┌─────────────────┼──────────────────┬─────────────────┐
              ▼                 ▼                  ▼                 ▼
         SQLite 检索库      int8 向量索引      bge-m3 ONNX      静态数据文件
         calr.db 1.6 GB    347 MB            1024 维            prototype/data
         BM25 倒排 877 万  法规 18,861        GPU: DirectML      权威源= laws/
                            条文 334,779       CPU 回退           派生=分卷/catalog
```

**双形态**：同一份前端代码，`http(s)://` 打开走后端，`file://` 打开走纯静态。
判断写在 `index.html` 的一段内联脚本里，结果存 `window.__CALR_API_MODE`。

## 二、前端架构：零构建 SPA

### 设计原则

| 原则 | 实现 |
| :--- | :--- |
| 零构建、零依赖 | 全部 classic `<script>`，挂在 `window.CALR` 命名空间下，无打包器 |
| 可 `file://` 运行 | 不用 ES module、不用 fetch 加载数据、不用 Service Worker |
| 渐进加载 | 条文分卷按需加载；进度里每载完一个分卷就静默重建索引并刷新当前页 |
| 失败可降级 | 后端不可用 → 纯静态；分卷加载失败 → 保留已有条文 |

### 模块划分

```
assets/js/
  app.js              启动、导航、主题、回到顶部、i18n 切换；D1 的异步引导也在这里
  core/
    store.js          数据层：合并多来源 → 建索引（lawById/articleById/lawsByCountry…）
    search.js         检索算法：分词、同义扩展、BM25、精确匹配加权、国别优先
    fulltext.js       分卷懒加载与译文合并
    qa.js             问答：检索 → 引用构建 → 要点抽取 → （可选）模型改写/重排
    rerank.js         BYOK 语义重排（用户自带 Key 时用模型筛掉词面命中的无关引用）
    llm.js            BYOK 配置与流式调用（默认 sessionStorage，可选持久化）
    api.js            后端适配层：同源自动识别、bootstrap/compact/search/qa
    router.js         hash 路由
    i18n.js           6 语种界面
    util.js           分词、转义、格式化、paragraphs（含 PDF 断行合并）
  views/              home / search / law / compare / assistant / terms / sources
  ui/                 icons / components（卡片、空态、面包屑、toast）
```

### store 的数据合并顺序

```
CALR_DATA_CORE / CALR_DATA_EXTRA（dataset-core/extra，约 1,600 部）
        + CALR_CN_CATALOG（中国 1,566 部，扁平 schema）
        + CALR_INTL_CATALOG（东盟 17,219 部，rich schema）
        + CALR_API_LAWS（API 模式后台补齐，来自 /api/laws/compact）
        + CALR_FULLTEXT_META（分卷元数据占位）
        ↓
   按 id 去重 → 合并字段 → 用分卷条文覆盖 catalog 条文 → 建索引
```

**去重必须同时对照「已加载的 store」**，否则 dataset-core 里已有的 1,600 多部会被重复计入
（曾导致国别卡片显示中国 1,594 而真实 1,586）。

## 四、检索链路

### 4.1 法规级检索（`/api/search`）

```
查询 q
  ├─ 分词：CJK 取 unigram + bigram，拉丁/泰/越取整词（与前端同一套口径）
  ├─ 同义扩展（semantic 模式）：数据→个人信息/数据保护/数据安全…
  ├─ BM25 倒排打分：k1=1.2, b=0.75，IDF 由倒排表实时计算
  ├─ 加权：
  │    ① 标题剥「中华人民共和国」前缀后精确匹配        +45
  │    ② 同名法规中国法优先（PRIORITY_COUNTRY=CN）     +25
  │    ③ 标题命中率 = 查询词出现在标题的比例 × 30
  │    ④ 无标题记录 ×0.55（多为采集缺失，避免占满首屏）
  │    ⑤ 有正文条文 +12~20（对数压缩）
  ├─ 相关性门槛：低于最高分 15% 丢弃（与前端一致）
  └─ 性能：先排序取前 800 名再做标题分词，避免上万候选逐个分词
```

**为什么标题要剥前缀**：东盟各国整理稿的中文标题直接就是「民法典」，
而中国是「中华人民共和国民法典」；不剥前缀，中国法在「标题精确匹配」上永远吃亏
（实测《民法典》曾排在 20 名之外）。

### 4.2 混合检索（`mode=hybrid`）

```
            ┌──────────────────┐
   查询 q ──▶│ BM25（法规级）   │─┐
            └──────────────────┘ │
            ┌──────────────────┐ │   RRF 融合
   查询 q ──▶│ bge-m3 → 余弦    │─┼─▶ score = Σ 1/(60 + rank_i) ──▶ 排序
            │ 18,861 条法规向量 │ │
            └──────────────────┘ │
                                  │   国别约束（问句提到某国则只留该国结果）
                                  └─▶ 返回（含 debug: rrf / bm25 / cosine / 两路排名）
```

**为什么 RRF 而不是加权求和**：BM25 分数量级 60–150，余弦 0–1，量纲不可比；
RRF 只看排名，无需归一化，也无需为每个查询调参。

### 4.3 问答（`POST /api/qa`）

```
问题 ──▶ bge-m3 编码 ──▶ 条文级向量检索（334,779 条，topk×6）
                              │
                              ▼
                        去重（正文前 80 字为键，跨重复法规记录收敛）
                              │
                              ▼
                        取 lawId + no 回查 SQLite，拿原文与条号标签
                              │
                              ▼
                        citations[] → 前端组装 answer（要点从条文原文抽取）
```

实测召回（前 1 条）：

| 提问 | 召回 |
| :--- | :--- |
| 数据安全法里关于数据分类分级保护的规定 | 《数据安全法》第 21 条 |
| 劳动法关于加班工资的规定 | 《劳动合同法》第 31 条 |
| 仲裁裁决的撤销情形 | 《仲裁法》第 58 条 |
| 泰国个人数据保护法关于跨境传输 | TH Section 29（**中文提问命中泰文法规的英文条文**） |

## 五、性能实测

### 首屏（同一份数据，两种打开方式）

| 视图 | API 模式 | 离线（file://） | 说明 |
| :--- | ---: | ---: | :--- |
| 首页 | **2,152 ms** | 4,454 ms | 快 2.1 倍 |
| 详情页 | 2,216 ms | — | API 兜底取整部法 |
| 国别页 | 2,207 ms | — | |
| 比对页 | 2,589 ms | — | |
| 检索页 | 2,259 ms | — | |

### 瓶颈分析与 D1

**关键事实**：首屏 6.4 秒的瓶颈**不是网络传输**（本地传输≈0），而是 **21 MB JS 的解析执行**。
其中 `intl-catalog.js` 独占 **15.9 MB**。

- 开 gzip：21.1 MB → 3.40 MB（压掉 84%），但**本地测试看不到任何提速**（6,432 → 6,819 ms，属噪声）
  —— gzip 省的是传输，本地传输耗时为 0。**gzip 的价值在真实网络部署**：
  10 Mbps 下首屏 25.7 s → 9.5 s（2.7 倍），2 Mbps 下 102.9 s → 21.8 s（4.7 倍）。
- **D1 才是本地提速的正解**：API 模式下**根本不加载** `intl-catalog.js`，
  改用 `/api/bootstrap`（2.7 KB）+ `/api/laws/compact`（后台补齐）。
  前端资源从 24.0 MB（42 脚本）降到 **7.39 MB**。

### 检索延迟（GPU 空闲时）

| 模式 | P50 |
| :--- | ---: |
| BM25（法级） | 256 ms |
| 纯向量 | 466 ms |
| RRF 融合 | 407 ms |
| 条文级问答 | 550 ms |

### 向量化吞吐（本机 GTX 1650 Ti，DirectML）

| 层级 | 条数 | 吞吐 | 耗时 |
| :--- | ---: | ---: | ---: |
| 法规级 | 18,861 | 35 → 15 条/秒 | 20 分钟 |
| 条文级 | 334,779 | 18~19 条/秒 | 4 小时 3 分 |

**纯 CPU 只有 6 条/秒**，GPU 快约 6 倍。用 **DirectML** 而非 CUDA：不需装 CUDA 工具链，
任何 DX12 显卡可用，仅 200 MB 依赖。

## 六、安全设计

### 后端（`backend/app/security.py`）

| 措施 | 实现 |
| :--- | :--- |
| **SQL 注入** | 全部参数化（24 处 `?` 占位符）；`in_clause(n)` 只产出占位符，禁止拼外部值 |
| **只读数据库** | `PRAGMA query_only=ON` |
| **CORS** | 默认只允许同源 + `file://` 的 `"null"`；生产用 `CALR_CORS_ORIGINS` 显式列域名；`allow_methods`/`allow_headers` 限定必要项 |
| **请求体上限** | `Content-Length > CALR_MAX_BODY`（默认 256 KB）→ 413 |
| **限流** | 按 IP 令牌桶（默认 120 次/分、突增 30）；只作用于 `/api/` |
| **QA 鉴权** | 设 `CALR_API_KEY` 后 `/api/qa` 必须带 `X-API-Key`；不设则开放（本地/演示） |
| **信息泄露** | `/api/health` 只返回安全配置的状态计数，不含任何密钥值 |

实测：恶意 Origin 的 `Access-Control-Allow-Origin` 为空（已拒绝）；连发 45 次出现 17 次 429。

### 前端

| 项 | 状态 |
| :--- | :--- |
| XSS | 33 处 `innerHTML` 赋值，753 处 `esc()` 转义；未发现直接把外部数据拼进 HTML 的路径 |
| **BYOK API Key** | **默认只进 `sessionStorage`**（关标签页即清）；用户显式勾选「记住」才写 `localStorage`；两者互斥无残留；输入框 `type=password` |
| Key 去向 | 直连用户自己填的 Base URL，**不经过 CALR 后端** |
| 硬编码密钥 | `prototype/` 内 0 个 |

### 仓库

`.gitignore` 排除 `_work/`（含模型、缓存、原始 PDF）与 `backend/data/`（DB 1.6 GB + 向量 347 MB）。

## 七、部署要点

```bash
# 服务器：4 核 8G 起（DB 1.6 GB + 向量 347 MB + BM25 计算，2G 内存是下限）
docker compose up -d --build      # 见 docker-compose.yml

# Nginx 反代必须开 gzip：静态站 16 MB 目录压到约 1.5 MB
gzip on;
gzip_types application/javascript application/json text/css;
```

**环境变量清单**

| 变量 | 默认 | 说明 |
| :--- | :--- | :--- |
| `CALR_DB` | `backend/data/calr.db` | 数据库路径 |
| `CALR_VEC` | `backend/data/vectors` | 向量索引目录 |
| `CALR_MODEL` | `_work/models/bge-m3` | 嵌入模型目录 |
| `CALR_CORS_ORIGINS` | 同源 + null | 允许跨域的来源，逗号分隔 |
| `CALR_API_KEY` | 空 | 设置后 `/api/qa` 需要 `X-API-Key` |
| `CALR_MAX_BODY` | 262144 | 请求体上限（字节） |
| `CALR_RATE_PER_MIN` / `CALR_RATE_BURST` | 120 / 30 | 限流参数 |
| `CALR_BATCH` / `CALR_MAX_LEN` | 16 / 160 | 向量化的批大小与截断长度 |

## 八、技术债

| 项 | 说明 |
| :--- | :--- |
| 前端仍加载分卷 | API 模式下已跳过 catalog，但条文分卷与 `bm25-idf.js` 仍在加载；彻底迁移需把条文也走 API |
| 无自动化测试流水线 | 8 个校验脚本靠手动跑，尚未接入 CI |
| 向量与库不同步 | 清理数据后未重跑条文级向量（4 小时），51 部切分法规仍是旧整段向量 |
| 单 worker | 生产建议 `--workers 4`，但需先评估 SQLite 只读连接的并发表现 |
| 无缓存层 | 高频查询未加 Redis 或进程内 LRU |
