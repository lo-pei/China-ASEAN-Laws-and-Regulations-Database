# B+ 完整部署（含 bge-m3 嵌入模型）

> 这是第 0 节里「B+ 完整」形态的专门步骤。通用部分（服务器规格、Nginx、验证清单、常见坑）
> 见 [07-部署指南.md](07-部署指南.md)，本文只讲**和 B 不一样的地方**。

---

## 1. 多出来的是什么

| 内容 | 文件 | 大小 |
| :--- | :--- | ---: |
| ONNX 图 | `model.onnx` | 0.7 MB |
| **ONNX 权重（外部）** | `model.onnx_data` | **2,161.8 MB** |
| 分词器 | `tokenizer.json` | 16.3 MB |
| 配置 | `config.json`、`special_tokens_map.json` | < 1 KB |
| **合计** | 5 个文件 | **约 2.18 GB** |

⚠️ **`model.onnx` 和 `model.onnx_data` 必须同时存在**。
只拷 `model.onnx` 会得到一个 0.7 MB 的空壳，ONNX Runtime 加载时报缺少外部权重。

## 2. 资源要求（比 B 高）

| 项 | B（无模型） | **B+（含模型）** |
| :--- | :--- | :--- |
| 内存 | 2 GB | **6 GB 起，8 GB 稳妥** |
| 磁盘 | 8 GB | **10 GB** |
| CPU | 2 核 | **4 核**（CPU 推理，核越多越快） |

**内存为什么涨这么多**：ONNX Runtime 要把 2.16 GB 的权重映射进内存，
再加上 SQLite 1.6 GB 与向量 0.35 GB。4 GB 机器会在并发问答时开始换页。

**没有 GPU 也能跑**：代码里执行提供者写死为 `CPUExecutionProvider`
（`backend/app/embedder.py` L62），不是 DirectML，也不是 CUDA。
所以云服务器和开发机走的是同一条路径，性能可以直接按第 4 节的数据预期。

## 3. 打包、传输、挂载

### 3.1 打包（本地）

模型在 `_work/` 下，默认不进 git，要单独打：

```powershell
# 运行必需
tar -czf calr-runtime.tar.gz prototype backend/app backend/Dockerfile `
    backend/requirements.txt backend/build_db.py backend/data

# 模型（约 2.2 GB，压缩后仍有 ~2.0 GB —— 权重本身高度不可压缩）
tar -czf calr-model.tar.gz -C _work/models bge-m3
```

### 3.2 传输

**2.0 GB 用 scp 会很慢**（家用上行 10 Mbps ≈ 30 分钟，20 Mbps ≈ 15 分钟）。
更实际的做法：

| 方式 | 说明 |
| :--- | :--- |
| **对象存储中转**（推荐） | 先传到 OSS/COS/S3，服务器上 `wget` 下载（机房带宽通常 100 Mbps+） |
| **服务器直连下载** | 如果模型有公开下载地址，直接在服务器上下（比从家里传快得多） |
| `rsync -P` | 断点续传，比 scp 稳 |

```bash
# 对象存储方式示例（阿里云 OSS）
ossutil cp calr-model.tar.gz oss://your-bucket/calr/
# 服务器上
wget -O calr-model.tar.gz "https://your-bucket.oss-cn-xxx.aliyuncs.com/calr/calr-model.tar.gz"
```

### 3.3 解包与目录

```bash
cd /opt/calr
tar -xzf calr-runtime.tar.gz
mkdir -p models && tar -xzf calr-model.tar.gz -C models
ls -lh models/bge-m3/
# 必须看到：model.onnx  model.onnx_data  tokenizer.json  config.json  special_tokens_map.json
```

## 4. 性能预期（实测，CPU）

在开发机（Windows，`CPUExecutionProvider`，与云服务器同一条代码路径）实测：

| 操作 | 延迟 |
| :--- | ---: |
| `/api/health` 可用（服务启动） | **1.6 s** |
| 首次语义检索（模型已在页缓存） | **0.2 s** |
| 稳态语义检索 | **约 150–270 ms** |
| keyword 检索 | 约 218 ms（中位） |
| hybrid 检索 | 约 520 ms（中位） |

⚠️ **首次容器启动会更慢**：模型要真正从磁盘读进来，
首次推理还要做一次图优化。Dockerfile 里 `HEALTHCHECK --start-period=25s` 就是为此留的余量。
如果服务器磁盘是机械盘，这一项会明显变长；SSD 上通常 5–15 秒。

**并发**：`--workers` 必须是 1（多 worker 会各自加载一份 2.16 GB 权重，内存直接翻倍）。
单进程靠 ONNX Runtime 内部多线程吃多核。线程数由 `CALR_THREADS` 控制
（`embedder.py` L58：`min(CALR_THREADS or 8, os.cpu_count())`，默认上限 8）。

```bash
# 4 核机器建议显式设成 4，避免默认 8 在核数少时反而拖慢
-e CALR_THREADS=4
```

## 5. 运行命令（B+ 版）

```bash
docker run -d --name calr \
  --restart unless-stopped \
  -p 127.0.0.1:8000:8000 \
  -v /opt/calr/backend/data:/app/backend/data:ro \
  -v /opt/calr/models/bge-m3:/models/bge-m3:ro \
  -e CALR_MODEL=/models/bge-m3 \
  --memory 6g \
  calr-api:1.0
```

- `-e CALR_MODEL=/models/bge-m3` **必须显式设置**。不设的话代码会回去找
  `<仓库>/_work/models/bge-m3`，容器里没有这个路径，语义能力会静默降级。
- `--memory 6g` 是软上限，防止内存异常时把整台机器拖死。
- 数据库与模型都用 `:ro` 只读挂载。后端已设 `PRAGMA query_only=ON`，SQLite 不会尝试写。

裸机 systemd 方式同样只要在 unit 里加一行：

```ini
Environment=CALR_MODEL=/opt/calr/models/bge-m3
```

# ① 模型真的被加载了（ready 应为 true，且 manifest.model 是 BAAI/bge-m3）

## 7. B+ 专属的坑

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| `vectors.ready = true` 但语义结果很差 | 索引是旧的（条文数与库不一致） | 见第 8 节，重建向量 |
| 启动就 OOM | 内存不足 6 GB，或误开了多 worker | 加内存 / 确认 `--workers 1` |
| `model.onnx_data` 找不到 | 只拷了 `model.onnx` | 两个文件都要在 |
| 语义检索 200 但和关键词结果一样 | 模型没加载，静默降级了 | 检查 `CALR_MODEL` 是否指向正确目录 |
| 首次请求超时 | 模型首次加载 + 图优化耗时 | Nginx `proxy_read_timeout` 调到 120s；健康检查用 `start-period` |
| 磁盘 IO 打满 | 机械盘 + 多并发读模型 | 换 SSD；或把模型放进内存盘 |

## 8. 什么时候需要重建向量

向量索引（`backend/data/vectors/`）和数据库是**两份独立数据**，必须同步：

```bash
# 看两份数据的条文数是否一致
curl -s http://127.0.0.1:8000/api/vectors | grep -o '"articles":[0-9]*'
curl -s http://127.0.0.1:8000/api/health  | head -c 200
```

**当前状态（本地实测）**：
  · 数据库 `articles` 表 339,351 条
  · 向量 `manifest.json` → article.count 334,779 条
  · **差 4,572 条**，即新增/重抓的这批条文语义检索覆盖不到，
    但关键词检索与条文浏览不受影响。
  · 法规级向量 18,861 条，比库里 18,785 部**多 76** —— 这是历史上删掉的法规残留，
    不影响检索（多余的向量找不到对应法规时会被跳过）。

重建向量的脚本在 `_work/phaseb/embed.py`（不在仓库内），
在 CPU 上跑全量约需数小时。如果你的数据不打算再变，可以不重建；
如果重抓了很多法规，建议重建一次再部署。
