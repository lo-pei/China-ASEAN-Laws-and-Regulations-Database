# 部署指南（云服务器）

> 本文写给「已有一台云服务器、要把本项目跑起来对外提供访问」的场景。
> 仓库里没有包含数据库、向量索引和嵌入模型（合计约 5 GB），所以部署的核心是**先准备好这些数据文件**。

---

## 0. 先决定要哪种形态

项目有三种运行形态，云端部署只需要前两种里的一种：

| 形态 | 需要什么 | 能力 | 体积 |
| :--- | :--- | :--- | ---: |
| **A. 纯静态** | `prototype/` 一个目录 | 检索、阅读、跨语言比对、术语对照、引注导出。**没有**语义检索与 AI 问答 | **913 MB** |
| **B. 后端服务**（推荐） | `prototype/` + `backend/`（含数据库与向量） | 上面全部 + 混合检索（BM25 + 向量 + RRF）+ 条文级语义问答 | **2.9 GB** |
| **B+ 完整** | 再加 bge-m3 模型 | 语义检索与问答的完整质量 | **5.1 GB** |

**如果服务器带宽/磁盘紧张，可以先用 A**：把 `prototype/` 丢给任意静态托管即可，
页面在 `file://` 下都能跑，不需要后端。

**如果要做 AI 问答和语义检索，必须用 B**。模型可以后补——没有模型时后端会自动降级
（语义接口退回法规级检索，问答退回关键词命中），实测五个接口与问答都返回 200。

---

## 1. 服务器规格建议

| 项 | 最低 | 推荐 | 说明 |
| :--- | :--- | :--- | :--- |
| CPU | 2 核 | 4 核 | BM25 是纯 CPU 计算；语义检索在无 GPU 时走 CPU 推理，比较吃核数 |
| 内存 | 2 GB | **4 GB** | SQLite 1.6 GB + 向量 mmap 0.35 GB；问答并发时更吃内存 |
| 磁盘 | 8 GB | **20 GB** | 运行文件 5.1 GB + 系统 + 日志 + 余量 |
| 带宽 | 1 Mbps | 5 Mbps | 首页首屏约 1 MB（API 模式） |
| 系统 | Ubuntu 22.04 / Debian 12 | 同左 | Docker 与 systemd 都按这两个写 |

**不需要 GPU**。有 NVIDIA GPU 时可以走 CUDA 版 onnxruntime 加速，但那是可选项，本指南不覆盖。

---

## 2. 把数据传到服务器

### 2.1 本地先打一个「只含运行必需」的包

**不要直接传整个项目目录**——`_work/` 里有 4 GB 以上的中间产物和模型副本。
在本地项目根目录执行：

```powershell
# 运行必需（约 2.9 GB）
tar -czf calr-runtime.tar.gz prototype backend/app backend/Dockerfile backend/requirements.txt backend/build_db.py backend/data

# 模型（可选，约 2.2 GB；放在 _work 下，默认不进包）
tar -czf calr-model.tar.gz -C _work/models bge-m3
```

如果你在 WSL / Linux 下，命令一样。

### 2.2 上传

```bash
scp calr-runtime.tar.gz user@your-server:/opt/calr/
scp calr-model.tar.gz   user@your-server:/opt/calr/     # 可选
```

**2.9 GB 用 scp 会比较慢**（家用上行 10 Mbps 约 40 分钟）。两个更快的办法：

- 先传到对象存储（OSS/COS/S3）再在服务器上下载
- 如果数据已在 Git 仓库里，直接在服务器上 clone（但 `backend/data/` 与模型被 `.gitignore` 排除，仍然要单独传）

### 2.3 服务器上解包

```bash
cd /opt/calr
tar -xzf calr-runtime.tar.gz
mkdir -p /opt/calr/models
tar -xzf calr-model.tar.gz -C /opt/calr/models     # 可选
```

解包后目录应长这样：

```
/opt/calr/
├── prototype/                 ← 静态站点（913 MB）
├── backend/
│   ├── app/                   ← FastAPI 应用
│   ├── data/
│   │   ├── calr.db            ← SQLite，1.6 GB
│   │   └── vectors/           ← 向量索引，366 MB
│   ├── Dockerfile
│   ├── requirements.txt
│   └── build_db.py
└── models/bge-m3/             ← 可选
```

## 3. 部署方式一：Docker（推荐）

### 3.1 装 Docker

```bash
curl -fsSL https://get.docker.com | sh
sudo systemctl enable --now docker
```

### 3.2 构建镜像

```bash
cd /opt/calr
docker build -f backend/Dockerfile -t calr-api:1.0 .
```

镜像本身只有几百 MB——数据库、向量、模型都是**运行时挂载**进去的，不打进镜像。

### 3.3 运行

**不带模型（轻量）**：

```bash
docker run -d --name calr \
  --restart unless-stopped \
  -p 127.0.0.1:8000:8000 \
  -v /opt/calr/backend/data:/app/backend/data:ro \
  calr-api:1.0
```

**带模型（完整语义）**：

```bash
docker run -d --name calr \
  --restart unless-stopped \
  -p 127.0.0.1:8000:8000 \
  -v /opt/calr/backend/data:/app/backend/data:ro \
  -v /opt/calr/models/bge-m3:/models/bge-m3:ro \
  -e CALR_MODEL=/models/bge-m3 \
  calr-api:1.0
```

> `-p 127.0.0.1:8000:8000` **只监听本机**，前面用 Nginx 反代。
> 想直接对外暴露就改成 `-p 8000:8000`，但**不建议**（见第 5 节的安全项）。

### 3.4 验证

```bash
curl -s http://127.0.0.1:8000/api/health
curl -s "http://127.0.0.1:8000/api/search?q=数据分类&size=3" | head -c 300
curl -s http://127.0.0.1:8000/ | head -c 100      # 应返回静态站点 HTML
```

## 4. 部署方式二：裸机 + systemd

不想用 Docker 的话：

### 4.1 装 Python 依赖

```bash
sudo apt update
sudo apt install -y python3.12 python3.12-venv
cd /opt/calr
python3.12 -m venv .venv
.venv/bin/pip install -r backend/requirements.txt
```

### 4.2 建 systemd 服务

`/etc/systemd/system/calr.service`：

```ini
[Unit]
Description=CALR API
After=network.target

[Service]
Type=simple
User=www-data
WorkingDirectory=/opt/calr
Environment=CALR_DB=/opt/calr/backend/data/calr.db
Environment=CALR_VEC=/opt/calr/backend/data/vectors
# 有模型时打开下面两行
#Environment=CALR_MODEL=/opt/calr/models/bge-m3
ExecStart=/opt/calr/.venv/bin/uvicorn backend.app.main:app --host 127.0.0.1 --port 8000 --workers 1
Restart=always
RestartSec=3

[Install]
WantedBy=multi-user.target
```

```bash
sudo chown -R www-data:www-data /opt/calr
sudo systemctl daemon-reload
sudo systemctl enable --now calr
sudo systemctl status calr
```

> **`--workers` 必须是 1**。多 worker 会让每个进程各自加载一份 BM25 统计与向量索引，
> 内存翻倍而且没有必要（单进程已能跑满 CPU 的多核做向量计算）。

## 5. Nginx 反向代理 + HTTPS

### 5.1 配置

`/etc/nginx/sites-available/calr`：

```nginx
server {
    listen 80;
    server_name law.example.com;          # 换成你的域名

    client_max_body_size 8m;

    # 静态资源长缓存（data/ 下的分卷文件名带 hash 或内容不变）
    location ~ ^/(assets|data)/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        expires 7d;
        add_header Cache-Control "public";
    }

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 120s;          # AI 问答可能较慢
    }
}
```

```bash
sudo ln -s /etc/nginx/sites-available/calr /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
```

### 5.2 HTTPS

```bash
sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d law.example.com
```

### 5.3 安全项（别漏）

后端默认带一层安全中间件，但有几件事要你自己做：

1. **CORS**：默认只允许 `null`（file://）与 `127.0.0.1:8000 / localhost:8000`。
   挂到域名后，前端与后端同源（都从同一个域名出），**不需要**加你的域名；
   如果你把前端单独托管到另一个域名，需要设环境变量：
   ```bash
   Environment=CALR_CORS_ORIGINS=https://law.example.com
   ```
2. **限流**：默认 120 次/分、突发 30，够用。被刷时调小：
   ```bash
   Environment=CALR_RATE_PER_MIN=60
   Environment=CALR_RATE_BURST=20
   ```
3. **`/api/qa` 是否需要 API Key**：默认关闭（公开可问）。
   如果怕被刷，设 `CALR_API_KEY=你的密钥`，前端会读取并在请求头带上。
4. **防火墙**：只开 22 / 80 / 443，**不要**把 8000 暴露到公网。

## 5.4 环境变量一览

全部由 `backend/app/` 直接读取，Docker 用 `-e` 传，systemd 用 `Environment=` 传。

| 变量 | 默认值 | 作用 | 什么时候要改 |
| :--- | :--- | :--- | :--- |
| `CALR_DB` | `backend/data/calr.db` | SQLite 数据库路径 | 数据放在别处时 |
| `CALR_VEC` | `backend/data/vectors` | 向量索引目录 | 同上 |
| `CALR_MODEL` | `<仓库>/_work/models/bge-m3` | bge-m3 模型目录 | **容器里必须显式设置**，否则路径不存在会静默降级 |
| `CALR_THREADS` | `8`（且不超过 CPU 核数） | 嵌入模型推理线程数 | 核数少于 8 时设成实际核数 |
| `CALR_CORS_ORIGINS` | 空（同源 + `null`） | 跨域白名单，逗号分隔 | 仅当前端与后端不同域名时需要 |
| `CALR_API_KEY` | 空（不校验） | 设置后 `/api/qa` 必须带 `X-API-Key` | 怕问答接口被刷时 |
| `CALR_MAX_BODY` | `262144`（256 KB） | 请求体上限 | 一般不用动 |
| `CALR_RATE_PER_MIN` | `120` | 每分钟请求数上限 | 被刷时调小；本地评测时调大 |
| `CALR_RATE_BURST` | `30` | 突发额度 | 同上 |

查看当前生效值：`curl -s http://127.0.0.1:8000/api/health` 里的 `security` 字段。

## 6. 上线前后验证清单

```bash
# ① 服务活着
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/api/health      # 200

# ② 静态站点能出
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/               # 200
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/assets/css/mobile.css   # 200

# ③ 检索能出结果
curl -s "http://127.0.0.1:8000/api/search?q=数据分类&size=3" | head -c 200

# ④ 法规条文能出（这条最容易漏，因为它走的是数据库而不是静态分卷）
curl -s "http://127.0.0.1:8000/api/laws/CN-DATA-2021/articles" | head -c 200

# ⑤ 语义能力状态
curl -s http://127.0.0.1:8000/api/vectors

# ⑥ 404 正常
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/no-such-page   # 404

# ⑦ 从公网访问
curl -s -o /dev/null -w "%{http_code}\n" https://law.example.com/
```

浏览器里再确认一遍：

- 打开首页 → 检索「数据分类」→ 点进《数据安全法》→ **应当看到 55 条、7 个章分组**
  （如果你只看到 4 条摘录，说明数据库没挂上或挂的是旧库）
- 切到英文 → 导航与正文文案应全部变英文
- 右上角切深色 → AI 页的内容区也应该是深色（不是白底）

## 7. 常见坑

| 现象 | 原因 | 处理 |
| :--- | :--- | :--- |
| 打开法规详情只有 4 条 | `backend/data` 没挂上，或挂的是旧库 | `curl /api/laws/CN-DATA-2021/articles` 看返回条数 |
| 语义检索报错 | 模型没挂但 `CALR_MODEL` 指向了不存在的路径 | 见 `/api/vectors` 的 `model` 字段；不存在时应当自动降级而不是报错 |
| 500 且日志提到 `unable to open database file` | SQLite 只读挂载后仍尝试写 | 确认用 `:ro` 挂载；后端已设 `PRAGMA query_only=ON` |
| 页面样式全丢 | Nginx 把 `/assets/` 也走了别的 location | 参照第 5.1 节，静态路径单独 proxy_pass |
| AI 问答 504 | Nginx `proxy_read_timeout` 太短 | 调到 120s |
| 内存被吃满 | 起了多个 worker / 多个容器 | 只保留一个 worker、一个容器 |
| 中文路径/客户端缓存 | 浏览器缓存了旧 JS | 部署后强制刷新，或给 `assets` 加版本号 |

## 8. 更新数据时怎么重新部署

数据有更新（比如重抓了法规、重建了索引）时，**不要**只替换 `prototype/`：

1. **静态分卷**（`prototype/data/`）
2. **SQLite 数据库**（`backend/data/calr.db`）← **最容易漏，漏了就是「静态数据新、接口数据旧」**
3. **向量索引**（`backend/data/vectors/`，条文数变了就要重建）
4. 重启服务（SQLite 句柄要重新打开）

```bash
# 本地重新打好包传到服务器后
sudo systemctl stop calr          # 或 docker stop calr
tar -xzf calr-runtime.tar.gz      # 覆盖
sudo systemctl start calr         # 或 docker start calr
curl -s "http://127.0.0.1:8000/api/laws/CN-DATA-2021/articles" | head -c 120
```

---

## 9. 一句话总结

**最小可用**：传 `prototype/` + `backend/`（含 data）→ `docker build` → `docker run` 挂 `backend/data`
→ Nginx 反代 + certbot → 跑第 6 节的 7 条 `curl`。

**模型可以后补**，不补只是语义检索降级，不会挂。
